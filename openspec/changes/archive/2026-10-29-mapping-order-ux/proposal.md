# Proposal

## Why

模型映射的权重排序把数字管理的负担丢给了管理员，且存在实际 bug：

1. **新增默认权重反向**：新增映射弹窗默认权重 = 当前映射总数（比现有都大），实际把新映射排到**最高优先级**，与"新增排最后"的直觉相反；管理员还要自己算数字、手动输入。
2. **编辑会悄悄改权重**：`showMappingDialog` 使用 `mapping?.weight || mappings.value.length`，拖拽排序会产生合法的 `weight=0`（排最后），JS `||` 把 0 误判为假值，编辑一条权重为 0 的映射并保存时权重被改成总数、顺序悄悄跳到最前。
3. **权重可重复**：后端创建/更新无唯一性校验，重复权重时 `ORDER BY weight DESC` 的路由顺序不稳定；且创建时 `weight=0` 被强制改为 1，与拖拽排序能产生 0 相互矛盾。

## What Changes

- 新增映射**自动排到末尾**：后端分配当前最小权重 - 1（不更新其他映射），创建请求无需携带权重
- 前端**隐藏权重输入字段**，顺序调整的唯一入口为拖拽排序
- 编辑映射仅允许修改指向（厂商/模型）与启用状态，不再触碰权重（消除零值误判 bug）
- 后端后台检查权重冲突并**自动顺延避让**：显式指定的权重与现有映射重复时，将本次操作的这条权重 +1 递增取第一个空位，**不阻断操作、不返回错误**；拖拽排序接口天然生成连续唯一权重，不受影响
- 清理创建时 `weight=0` 强制改为 1 的旧逻辑
- 不增加任何数据库唯一约束（避免约束在拖拽逐行更新的中间态报错、阻断操作）

**BREAKING**（轻微）：创建/更新映射 API 的 `weight` 字段语义变化——未携带时自动分配（创建为最小权重排末尾），携带且冲突时自动顺延避让（响应中的权重可能与请求值不同）。现有前端同步修改，无用户可见影响；仅直接影响绕过控制台直接调用管理 API 的脚本。

## Capabilities

### Modified Capabilities

- `model-mapping`: 权重分配规则变化——新增自动排末尾（取最小权重 - 1）、编辑不修改权重、权重冲突自动顺延避让；原"默认权重为 1"的行为被"自动分配末尾权重"取代。

## Impact

- `server/internal/handler/model.go`：`CreateMapping`（自动分配 + 冲突避让）、`UpdateMapping`（冲突避让）、删除 `weight==0` 强改逻辑
- `web/src/views/Models/Detail.vue`：映射弹窗移除权重字段、修正 `showMappingDialog` 默认值逻辑
- 无 DB schema 变更、无唯一索引（用户明确不加数据库约束；唯一性由后台检查 + 自动避让保证）
- API 响应结构不变，仅请求语义变化
